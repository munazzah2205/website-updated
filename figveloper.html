The Problem

There is a workflow that every designer knows and nobody talks about. The friction between vision and execution.

"I spent four hours explaining why a 4px gap was 6px in production. It wasn't about the pixel—it was about the process. I realized that until we bridge the gap between Figma's JSON and the browser's DOM, we are just guessing."

— Munazzah Zainab, UI/UX Designer

01

Context Switching

You hold CSS values in short-term memory while switching between browser and Figma. By the time you arrive, the precision is already gone.

02

Lost Documentation

Word documents and email attachments have no connection to the element they describe. Discrepancies are written, sent, forgotten, and repeated.

03

Invisible Resolution

When the new build arrives, there is no record of what changed. Every review cycle starts from zero. The loop never closes, it just restarts.

Where FIGVELOPER sits.

The Solution

A unified workspace that connects Figma directly to the live build. One surface. Every stakeholder. No tab switching.

Side-by-Side Comparison Canvas

Figma and the live site. Same viewport, same zoom, same moment. The gap between design intent and built reality — visible instantly.

Element Inspector with CSS Output

Click any element. See what Figma specified vs what the browser computed. Selector, expected value, actual value, no document needed.

Annotation Pinning with Comment Threads

Right-click any element to raise a pin directly on its border. Set severity, assign it, discuss it, resolve it — without leaving the canvas.

Discrepancy Log

Every pin becomes a tracked issue. Filterable by screen, severity, and status. The review document that used to live in email — now permanent and element-anchored.

Project Dashboard

Total screens, open issues, resolution rate — one screen, no digging. Project health readable in under five seconds.

Technical Constraints

FIGVELOPER operates at the boundary of browser security, third-party APIs, and live environments. These are the real-world limitations every implementation must navigate.

Figma API Dependency

The Personal Access Token can expire or be revoked at any time. If read access is lost mid-session, the left canvas fails entirely, requiring a full reconnect flow.

iframe Embedding Restrictions

FIGVELOPER is designed for localhost and staging environments — where design QA actually happens and iframe restrictions don't apply. A connection fail state handles edge cases gracefully

Cross-Origin DOM Inspection

Browsers block cross-origin iframe content access natively. Element-level CSS inspection requires either a browser extension, a proxy layer, or script injection on the live site.

CSS Computed Value Accuracy

The Inspector reads computed CSS, not authored values. Inheritance, overrides, and specificity conflicts can create misleading discrepancies.

Information Architecture & User Flows

FIGVELOPER has two distinct entry points and three core workflows. Admin responsibilities and team workflows stay on separate paths — they never overlap.

Entry Points

Admin Setup Flow

Landing Page → Create Account → Project Setup Step 1 (Connect Figma) → Step 2 (Add Live URL) → Step 3 (Invite Team) → Comparison Workspace.

Member Entry Flow

Invite Email → Accept Invitation → Comparison Workspace → (Return visits) → Login → Member Dashboard → Comparison Workspace.

Core User Flows:

QA Review — Designer

Select Screen → Select Frame → View Split Canvas → Click Element → Inspect CSS → Right-click → Raise Pin → Set Severity → Assign to Developer → Pin appears on canvas.

Resolution — Developer

Receive Notification → Open Pin in Workspace → View Properties Diff → View CSS Output → Fix in Codebase → Mark Resolved → Designer Notified → Confirm or Reopen.

Log Review — Designer / PM

Open Log → Filter by Status/Severity → Click Row → View Pin in Context → Open Comment Thread → Update Status.

Dashboard Review — Project Manager / Scrum Master

Login → Open Project → View Project Dashboard → Read Issue Summary → Check Severity Distribution → View Recent Activity → Identify Blockers.

Designing with Google Stitch AI

Seventeen screens. Six user flows. Google Stitch generated the base structures. Every decision inside those structures was made by hand.

01 / Define

System Framework

The full design system — colours, typography, spacing, component rules — was documented before a single screen was generated. Stitch needed the complete token set upfront. Without it, screens drifted. With it, they held.

02 / Generate

Base Iteration

Every screen was prompted zone by zone. Specific component briefs, not vague descriptions. The more precise the input, the less correction was needed on the other side.

03 / Review

Audit & Align

Stitch hallucinated consistently in one area — copy. Feature lists, notification labels, button text — all required a full content audit on every screen. The layout held. The words never did.

04 / Refine

Editorial Polish

Hover states, disabled states, edge cases, badge consistency across seventeen screens — none of this came from prompts. Stitch built the skeleton. The craft was manual.

What Stitch did. What it didn't.

Fast at structure. Blind to decisions.
Layout, hierarchy, component placement, Stitch handled these well. What it could not do was decide which information belongs where, what a disabled state should communicate, or why Courier New appears in one panel and not another. Those answers had to exist before generation began.

60%

Time Saved

Generating base screen layouts with Stitch took roughly half the time compared to designing from scratch in Figma.

40%

Of Total Effort

The manual refinement phase, the 40% that came after generation, produced 80% of the perceived visual quality of the final screens.

Key Design Decisions

1. Right-Click to Pin, Not a Hover Toolbar

A hover toolbar triggered on every inspection hover. Right-click makes the intent deliberate, separating inspection from annotation at the interaction level.

2. CSS Output is Automatic. The Diff is Human.

Automated scanning can't distinguish a real bug from intentional responsive behaviour. CSS output is automatic. The judgement call stays human.

3. The Discrepancy Log Opens Unfiltered but is Built to be Filtered

All discrepancies are visible on open. The summary cards—Assigned, In Progress, and Resolved—are not just counters. Clicking them filters the table to that status.

4. Severity is Required, Not Optional

The pin form does not submit without a severity selection. Forced structure at the point of creation produces usable data downstream.

5. Status and Severity Colours Never Overlap

Two colour systems run simultaneously across the product. When amber appeared in both, In Progress was remapped rather than letting either system compromise the other.

The Roadmap Ahead

V1 deliberately scoped for the core QA loop — compare, pin, track, resolve. Here is where FIGVELOPER goes next.

Jira & GitHub Integration

Every discrepancy in the log becomes a ticket or a PR comment automatically. The QA trail and the development workflow live in the same system.

Sprint Wise Tracking

Projects gain a time-bound layer. Discrepancies are assigned to sprints, and the dashboard reflects what was raised, resolved, and carried over each cycle.

Reflection

FIGVELOPER started as a workflow frustration across three projects and ended as a focused tool that solves exactly that problem. Not more, not less.

The technical constraints are real — iframe restrictions and API dependency are ceilings V1 cannot break through by design alone. Naming them honestly was more important than designing around them.

The sharpest lesson was about scope. Every feature that didn't make it in, browser extension, real-time collaboration, automated regression, would have made FIGVELOPER harder to use, not easier. A tool that does one thing without friction is more valuable than one that does everything poorly.
